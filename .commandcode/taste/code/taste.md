# Code Preferences

- Domain-boundary doctrine for reference/communication surfaces (Chat, Comment): such a surface OWNS only communication state — the resource reference/occurrence a message is about, the operation, the resource identity, a navigation target, and a server-built DISPLAY fallback — and never the owning domain's business truth (price, inventory/availability, seller commercial state, order, payment, transaction, settlement, commerce business rules/authorization/lifecycle). Validation is layer-scoped: the surface validates only its OWN reference contract + communication permission ("is this reference well-formed and allowed into the conversation?") and never duplicates the owning domain's business validation ("is the resource active, what is its price, can it be bought?"). When existing code violates the boundary it is REFACTORed to the canonical design — never kept merely because it already exists — and projection DTO/entity fields are classified one by one (required for display/reference vs required-but-owned-elsewhere vs obsolete vs ambiguous) rather than mass-deleted. Confidence: 0.72

- Prefers server-authoritative, viewer-aware display projections: the backend resolves what is safe/relevant to show a specific viewer (e.g., LIVE vs TOMBSTONE) by delegating to the owning domain, and the client only ingests and renders it — never deriving the resource representation locally. Any persisted fallback snapshot is understood as historical/communication DISPLAY only, never a source of truth for current price/availability/transaction state, and a malformed projection is dropped as display decoration rather than failing the whole message. Confidence: 0.6

- Preserves out-of-scope/protected callers by shape: when a caller in a protected or parallel-work domain depends on a shared API signature, the signature is NOT changed and the protected implementation is not touched — a new, distinctly-named entry point is added inside the in-scope domain and both public entry points delegate to a single private core, rather than forking behavior or introducing a Legacy/Compat variant of the converged path. Confidence: 0.62

- Preserves batch/aggregate resolution and existing query-count acceptance contracts: a per-message lookup (1 message → 1 query) is rejected when the architecture already provides a batch/aggregate resolver, the aggregate resolver is kept as canonical, and the existing ordering/pagination authorities plus the query-count acceptance tests are maintained as a performance contract rather than relaxed. Confidence: 0.65

- Dead UI residue purge (Flutter): an unreferenced widget/helper class inside the audited presentation directory that has zero references across `lib/` and `test/` AND is not exported by the package barrel is provably dead obsolete residue and is hard-deleted (e.g., `ContentCallbacks`, a dead helper from an older "post screen" composer) — provenance is not required, but the absence must be proven before deleting. The purge is proven proportionally by a symbol + file-name reference sweep (0 matches), a barrel/export check, and a scoped `dart analyze <audited-dir>` returning "No issues found!". Legitimately-distinct widgets living in the same tree (a composer SCREEN vs a create-*menu* bottom sheet; generic commerce card primitives; a compact cross-type search row; share/object preview cards; a repost attribution bar) are preserved as DISTINCT surfaces with their own user-facing responsibility rather than deleted as duplicates. Confidence: 0.65

- Legacy user-facing copy on a canonical surface is escalated, not rewritten: when a canonical screen still renders a legacy Post-rooted label (e.g., `'Posted on ${date}'` in the Content detail screen, against an Owner-locked "Content, not legacy Post/Request terminology" rule) and no canonical replacement phrasing is established anywhere in the app, the executor does NOT invent new copy or rename it — it is reported as the single open contract detail requiring an Owner-approved label. Such a wording-only finding is its own decision category (COPY WITHOUT CANONICAL REPLACEMENT: leave unchanged, report as a small Owner decision that must NOT block or abort the rest of the scope — "do not block the whole scope because of such wording"), and non-user-facing residue — internal identifiers (postVisibility, post_location) and stale doc comments describing controls/behavior that no longer exists (e.g., a "Request uses auto location" comment beside a removed "allow comments switch") — is left untouched in the user-facing residue sweep and reported informationally rather than edited. Confidence: 0.6

- Two entrypoints with different idempotency contracts legitimately keep SEPARATE create primitives: application-level idempotency is a per-entrypoint contract, not a global requirement, so a non-idempotent internal create primitive is KEPT when its caller's entrypoint deliberately owns a different idempotency contract — especially when the canonical idempotent variant is contract-bound to hard-reject without a key/non-nil idempotency repo and is therefore NOT substitutable on the non-keyed path (converging would require inventing new product/API idempotency semantics, an Owner-tier decision). The decision is made on actual responsibility: non-idempotency alone is never evidence of obsolescence ("do not assume application-level idempotency is required for every internal function merely because public POST creation requires it"), and an existing production caller alone is never evidence of distinctness ("do not preserve a non-idempotent internal function merely because it is an existing production caller") — a concrete distinct responsibility must be proven, otherwise migrate the callers and purge. Confidence: 0.7

- When a delivery-layer (HTTP handler) pre-check duplicates an application/service-layer canonical authorization, the pre-check is OBSOLETE and is purged: a weaker, fail-open, partial-coverage subset (e.g., covering only the top-level content-author pair, missing reply-parent-author coverage) of a fail-closed canonical service authority is still a duplicate — the canonical service authorization is preserved, the deleted check is never replaced with another duplicate check, and "extra safety" / "just in case" / historical behavior / old tests are not sufficient reasons to keep it. Confidence: 0.7

- Purges a competing authority by making the old state UNREPRESENTABLE rather than merely rejected at runtime: the mode parameter/type is removed from the constructor entirely (compile-enforced) so an empty/omitted/default argument can no longer silently select the old business mode — no runtime validation branch, `if mode == ""` fallback, or compatibility shim left behind. Confidence: 0.75
- Each independent business gate/channel must be asserted DIRECTLY in tests: a negative result on one channel (e.g., no DB insert) is never inherited as proof for a sibling channel (e.g., push) — the second gate is asserted directly with a counting mock and deterministic wait, per the owner's rule "a push assertion must be real, do not merely infer DB insert false therefore push probably false". Confidence: 0.75
- Deadlines/expiries that are derivable from a canonical timestamp are computed at enforcement/read time and never persisted as a stored deadline column: a stored deadline field is treated as a duplicate/second deadline authority and dropped, not kept in sync — one derived formula (e.g., end_at + 24h), no extension, no second deadline authority. Confidence: 0.7
