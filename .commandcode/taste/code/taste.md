# Code Preferences

- Deadlines/expiries that are derivable from a canonical timestamp are computed at enforcement/read time and never persisted as a stored deadline column: a stored deadline field is treated as a duplicate/second deadline authority and dropped, not kept in sync — one derived formula (e.g., end_at + 24h), no extension, no second deadline authority. Confidence: 0.7
- Deadline/expiry workers must be deterministic and idempotent using existing PostgreSQL locking/transaction patterns — phase-1 short transaction to fetch candidate IDs FOR UPDATE SKIP LOCKED, then per-row processing in its own transaction that re-verifies status under FOR UPDATE before mutating — and no distributed locking framework is introduced when DB-level row locking already suffices. Confidence: 0.65
- Canonicalizing a state machine requires a test matrix that covers every allowed transition outcome (success and each failure class), every side-effect reset on the failure path (order binding, winner, current bid, resolution markers, flags), relist restart invariants, deadline boundary invariance (e.g., quotes at multiple timestamps all yielding the same deadline), race/idempotency cases, plus a repo-wide sweep proving no stale test still pins a removed state/term. Confidence: 0.65
- Prefers behavioral tests that exercise real logic over brittle source-string scans; source-scan guards are considered weaker proof (e.g., a "fee removed" guard that only greps source was flagged as insufficient evidence). Confidence: 0.7
- Prefers behavioral widget tests over brittle source-string tests when runtime visibility is governed by a shared widget. Confidence: 0.6
- Prefers removing unsupported/deceptive UI affordances entirely rather than disabling them, stubbing them as "coming soon", or mapping them onto another lifecycle action. Confidence: 0.7
- Prefers derived logic to consume the canonical formula/primitive directly rather than reimplementing the formula; reimplementations are classified as duplicate/conflicting authorities and must converge onto the canonical semantics, never become a second authority. Confidence: 0.8
- Requires exactly ONE authoritative financial snapshot per domain; dead/non-authoritative fields must not simply be repopulated and kept with unchanged consumers — consumers must be rewired to the canonical representation (e.g., pricing token, ledger, coins domain) instead of treating dead columns as authority. Confidence: 0.8
- Accounting code must trace a real funding/source explanation for every ledger movement: GATEWAY_CLEARING (actual gateway cash) may only be debited by amounts actually funded — never invent funding to make balances pass, and never patch shortfalls with balance guards or negative-balance exceptions. Confidence: 0.85
- Prefers reusing an EXISTING canonical authority/account as the source for a new funding obligation over inventing a new one; never repurpose an account merely because its name sounds plausible — verify its established semantic meaning (e.g., PLATFORM_BANK = platform's own bank holdings via withdrawal-payout semantics) — and if no existing authority legitimately fits, STOP and report instead of creating a new accounting authority. Confidence: 0.75
- Prefers DB-level idempotent dedup via ON CONFLICT DO NOTHING + rows-affected detection over catching unique-violation errors after the fact: a SQL error aborts the transaction, so the subsequent Commit fails ("commit unexpectedly resulted in rollback") even when the duplicate is treated as success — duplicate/concurrent delivery must be a clean no-op. Confidence: 0.7
- Requires exactly-once, replay-idempotent lifecycle transitions (e.g., coin reservation consume → order_spend → balance deduct): each side-effect happens exactly once, and a replayed/duplicate settlement verifies the prior side-effect already exists and returns success instead of erroring. Confidence: 0.6
- Never weakens or removes balance/constraint guards (e.g., financial_accounts.balance >= 0); when a source account must fund platform benefits, give it a legitimate opening reserve float (mirroring the established BANK_SETTLEMENT pattern) so the constraint holds honestly. Confidence: 0.6
- Prefers converging the HTTP wire contract to a locked spec by adding canonical snake_case/JSON tags directly onto the existing canonical domain and aggregate types (so the live handler emits the locked shape) rather than maintaining a separate response-DTO layer; a rich response DTO that only re-serializes the canonical domain model is a duplicate authority to delete, not keep alongside it. Confidence: 0.8
- Separates password policy validity ("does this password satisfy the minimum policy?") from password strength ("how strong does it appear to the user?"): strength tiers/scoring are UX for a later stage and must not be introduced while converging policy validation. Confidence: 0.8
- Never weakens the application's locked password policy to match a weaker external floor (e.g., Firebase min-6 vs app min-8): policy-failing passwords are blocked before the external system is called, and the external system is never claimed to enforce the app's stricter policy. Confidence: 0.85
- Applies registration-style password policy validation only to password creation/change surfaces, never to login: an existing credential may legitimately predate the policy, so login gates on non-empty input and defers acceptance to the auth authority. Confidence: 0.75
- Converges validators onto ONE canonical authority with thin delegating wrappers ("converging, not layering another validator"): a validator with legitimate specialized semantics keeps its wrapper but its policy portion delegates to the canonical policy — never a second validator. Confidence: 0.8
- Requires convergence tests to prove production consumers actually delegate to the canonical authority (not merely that the authority passes its own unit tests), so a future agent cannot silently reintroduce a duplicate inline rule — e.g., a test that would catch a future regression wiring `onChanged` only to the password field while forgetting the confirm field. Confidence: 0.75
- Keeps pure domain/presentation logic in a pure, deterministic evaluator/helper rather than a service/repository/provider layer; the evaluator stays free of UI/framework dependencies, with color/rendering mapping delegated to the widget layer. Confidence: 0.7
- Strength/UX classification must never gate submission or redefine policy validity: isStrong ≠ isValid — a password can be policy-valid but not Strong, or classified Strong while policy-invalid; the policy authority remains the only submit gate. Confidence: 0.8
- Defines and documents a canonical empty-state for inputs: empty values render a neutral state, never a misleading warning/classification (e.g., an empty password shows no "Weak" label). Confidence: 0.65
- Optional text/media-reference columns treat an explicit empty string as the canonical "clear this field" signal that persists as SQL NULL (never an empty string), so a cleared reference hydrates back as nil — this applies uniformly to optional profile/media columns (avatar, cover photo, bio, ...). Confidence: 0.6
- Removal of a media reference (e.g., cover photo) is a database-reference clear, never a storage delete: the client sends an empty-string update for the field (backend → NULL) and no delete endpoint/object-delete call exists; upload services therefore drop their S3 delete methods entirely. Confidence: 0.6
- Wire contract invariant for media references: persistence carries the STORAGE KEY (e.g., `images/profile-covers/{userId}.jpg`), while resolved read/CDN URLs are display-only and never persisted — the client distinguishes them and tests assert the persisted value remains the key. Confidence: 0.7
- Realtime UX feedback (e.g., strength meters) must derive directly from the current input value and update while typing — never keyed to blur, submit, or Form validation; realtime behavior is proven by widget/state tests that type through a real field without blur or submit. Confidence: 0.7
- Converges reusable UI components (widgets, indicators) onto ONE canonical widget/engine shared by all surfaces instead of creating parallel per-surface implementations; labels, classification, calculation, and transition behavior must be identical everywhere. Confidence: 0.7

- Password-confirmation matching compares the exact current values with plain string equality — never trim/lowercase/normalize/transform, and never imports policy or strength semantics: password validity, password strength, and confirm-password matching are three separate concerns/authorities that must not cross-import. Confidence: 0.8
- Prefers implementing realtime behavior self-contained inside the canonical reusable widget (owning its own controller listeners) over parent-passed rebuild conditions or a global state service — the smallest correct change that keeps the component locally reusable across all surfaces. Confidence: 0.75
- Error-state UX: transient/bootstrapping conditions must not be rendered as a terminal-looking error while recovery/retry is still in flight, but genuine failures must remain truthful and visible — never hide a real outage behind a non-terminal state; the terminal error page is gated until the canonical retry budget is exhausted, and the loading/pending presentation is kept while retries are scheduled. Confidence: 0.8
- Prefers exposing retry/status signals to the UI as pure read-only getters over existing controller state instead of adding new states or changing state-machine semantics; a new state is justified only when an audit proves existing states cannot satisfy the requirement. Confidence: 0.7
- Requires a single owner for a recovery/retry loop: manual retry must funnel through the same canonical recovery entry as automatic retry (no parallel timers/requests), and UI retry triggers are disabled while a cycle is pending so manual and automatic loops cannot overlap. Confidence: 0.75
- Hard-coded environment-specific values (e.g., a dev LAN IP) are never a permanent config authority: audit the existing configuration mechanism first, then converge the value through it (e.g., --dart-define overrides + platform-aware defaults), bounded — without redesigning the global configuration. Confidence: 0.75
- Startup/availability fixes must stay within the existing architecture — no new cross-cutting layers (ConnectivityService, health-check polling, global retry interceptor, offline mode) unless a requirement provably cannot be met otherwise. Confidence: 0.7
- Enumerates compile breaks completely with BOTH go build (non-test packages) and go vet (which also parses test files that build skips); corruption left by a crashed bulk text replacement is detected by searching for characteristic patterns (e.g., sed delimiter letters f/r replacing quotes inside string literals and import blocks) and confirming the damage is confined to a small verified file set before reporting it as a blocker. Confidence: 0.75
- Separates format validation from normalization and verification: a canonical field validator answers only "is this well-formed?" (format-only, no network, no availability/verification features), while E.164 normalization, OTP/verification, and availability checks belong to a separate service; a post-normalization gate (e.g., PhoneVerificationService's E.164 check) is a verification-path check — not a format-validator consumer — and is left untouched during format convergence. Confidence: 0.8
- When canonicalizing a rule, preserves the factual behavior of the existing real production consumer (e.g., HTTPS-or-localhost URL policy) and never silently broadens or narrows policy; if the existing behavior is ambiguous, STOP and report rather than inventing a rule. Confidence: 0.8
- Canonical validator tests must cover a full accept/reject matrix — clearly valid, clearly invalid, boundary cases (e.g., phone digit counts at 8/9/12/13), empty/whitespace input, prefix variants, formatting tolerance, and invalid schemes — not just happy paths. Confidence: 0.7
- Repairing code corrupted by an interrupted bulk text replacement must use precise, per-file edits — never broad/global search-replace across a file; global regex passes on large files cause cascading collateral damage (eaten opening parens, mangled string literals, broken composite literals) that is worse than the original corruption. Confidence: 0.85
- For a file with pervasive mechanical corruption (hundreds of mangled string literals/import blocks), full-file reconstruction from the complete pre-edit read is safer than iterative regex patching — convert the mechanical corruption (e.g., f...f / r...r fenced literals → quoted strings) in one clean content-preserving pass, then verify with gofmt. Confidence: 0.7
- When writing Go files from PowerShell/CLI, preserve UTF-8 without BOM explicitly; default Get-Content/Set-Content round-trips double-encode non-ASCII characters (e.g., → becomes â†' mojibake), which corrupts string literals and comments. Confidence: 0.65
- Before finalizing a reconstructed file, verify that helpers it references (e.g., mustJSON) are actually defined elsewhere in the same package — cross-file symbol existence is checked, not assumed, before declaring the reconstruction complete. Confidence: 0.6
- Security findings are classified by content and actual usage, never by filename alone: Firebase client configs (google-services.json, GoogleService-Info.plist, firebase_options.dart) hold public-by-design client keys and correctly stay tracked, and dev-only credentials matching the local docker-compose default are SAFE_CONFIG — only genuinely exposed secrets are removed, and files are never deleted merely because their names look sensitive. Confidence: 0.8
- Hardcoded API keys in tracked source are replaced by build-time injection from an untracked local source (e.g., MAPS_API_KEY in local.properties → Gradle manifest placeholder) with a placeholder fallback so CI builds stay valid — a live key is never committed. Confidence: 0.8
- Enforces domain invariants at the database level wherever PostgreSQL can express them (partial unique indexes for "one active X per Y", NOT NULL + FK provenance, enum type membership, append-only/immutable triggers for historical records) — never relies on application-level duplicate/invariant checks alone when the DB can enforce them. Confidence: 0.8
- Adds only fields and constraints with a clear business purpose; speculative "might be useful" columns/constraints are not added just because they could help later. Confidence: 0.7
- Migration SQL constraints must use only IMMUTABLE functions: index predicates (partial indexes) reject STABLE functions like `now()` (SQLSTATE 42P17) — an index predicate such as `WHERE restricted_until > NOW()` is a deterministic migration defect; partial indexes on timestamp-expiry conditions must use an IMMUTABLE predicate or be dropped, and PostgreSQL must never be tricked with another STABLE time function. Confidence: 0.85
- Index design is driven by the actual SQL query patterns of the table's consumers, never by assumption or speculative future use: every repository query is inspected first; when an existing constraint index (e.g., UNIQUE(user_id)) already serves the sole demonstrated access path (WHERE user_id = $1), an invalid/unneeded extra index is removed entirely rather than replaced with a compound index — no index is added without demonstrated query value, and time-dependent "is it active?" evaluation belongs in application code, not in a partial-index predicate. Confidence: 0.75
- Backend/service layer is the sole validation authority for canonical business values (locked enums, taxonomies, reason codes): the backend enforces them server-side, and client-side checks are UX-only pre-filters that are never the sole validator — a client that is the only gate for a canonical rule is a defect to fix, not a convenience to accept. Confidence: 0.7
- Historical evidence/preview snapshots store only minimal immutable context metadata (author/username/title/status preview) captured at record time and are never treated as authority for current state — the live target object remains authoritative; no full-object archival, event sourcing, domain versioning, or duplicate-copy system is added just to preserve historical context. Confidence: 0.6
- For a stale test blocked by a concrete dependency field (fake uninjectable), prefers restoring the fake-injection seam through the live canonical interface — the one the impl already satisfies and asserts — over rewriting unit tests to drive the real repo through canned SQL/row fakes; a one-line production field-type change that touches no business behavior is acceptable to keep unit coverage, while any change to business behavior or weakening of assertions is not. Confidence: 0.65
- Cleaned/rewritten tests must serve as architecture documentation: they describe CURRENT behavior through CURRENT production seams, avoid implementation details that no longer exist, and pass the "fresh agent" criterion — a new reader should learn the correct architecture from the test alone (e.g., stale-result protection is proven through the current hydration-generation guard, never through removed epoch/principal-check params). Confidence: 0.7
- Go dependency-deadness verification searches subpackage import paths, not just the module root string: `"golang.org/x/time"` yields zero hits while `"golang.org/x/time/rate"` is an active consumer (rate_limiter.go), so a root-path-only grep falsely declares a dependency dead — confirm with `go mod why`/`go mod tidy` and preserve anything with a subpackage consumer. Confidence: 0.8
- Flutter plugin deadness requires more than zero Dart imports: a plugin with native code (e.g., midtrans_sdk) is registered in GeneratedPluginRegistrant and compiled into the binary even with zero Dart callers; registrants are regenerated by `flutter pub get` (iOS/Android variants typically untracked while linux/macos are tracked), so removal is proven by removing from pubspec.yaml + `flutter pub get` + confirming lockfile entries gone + `flutter analyze` passing. Confidence: 0.7
- After removing a direct dependency, a package retained in the lockfile as `transitive` (pulled by an active package — e.g., crypto via dio/firebase, zod via eslint-plugin-react-hooks) is correct, not residue; lockfile review distinguishes legitimate transitive retention from orphaned transitives and never blindly removes unrelated transitive entries. Confidence: 0.7
- Canonical constructor/API convergence fixes stale callers to the ONE canonical signature and never introduces versioned variants (`*Legacy`, `*Compat`, `*V2`), variadic/optional legacy arguments, test-only adapters, or compatibility overloads to make old tests compile; stale tests/helpers/fixtures are updated to the current domain instead, and a signature is never changed merely to satisfy a legacy test. Confidence: 0.7
