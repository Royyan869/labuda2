# Communication Preferences

- Requires structured audit/implementation reports: an exact verdict code, decision matrices, exact file paths/symbols/line ranges, exact commands run with exit codes, and explicit "FILES CHANGED: NONE" / "DATABASE CHANGED: NONE" / "MIGRATIONS CHANGED: NONE" statements (evidence-only audits must not start a DB process); a stopped report must enumerate the exact contradiction, files/symbols, runtime/source evidence, affected ledger accounts, the mathematical identity, why the existing model cannot satisfy the canonical contract, and the exact owner decision required. Confidence: 0.95
- Wants audit deliverables written to the explicitly-designated report file (e.g., the named audit .md) and also summarized in chat — not left as file-only artifacts without a chat summary. Confidence: 0.7
- "Do not infer" — audits must cite exact file paths, symbols, and code excerpts rather than paraphrased claims. Confidence: 0.85
- Audit reports must explicitly answer each yes/no question posed in the audit brief (e.g., "can real orders persist discount_amount = 0 despite a non-zero discount?", "is escrow_amount actually persisted?", "does total_before_coins_amount match (P-D)+S?") with a definitive, proof-backed determination — not merely describe the code. Confidence: 0.65
- Wants findings classified into precise categories rather than a flat list; audits request a candidate map separating canonical authority, valid derived values, existing funding mechanisms (existence ≠ canonical — an existing mechanism is not canonical merely because it exists), duplicate authorities, conflicting authorities, and legacy/zombie/incorrect representations — each item assigned exactly one category with an explicit UNKNOWN fallback — plus an explicit kill list of everything that must eventually be removed (and a protected must-not-remove list) so the rejected model cannot be resurrected. Confidence: 0.85
- When a mistake is discovered, wants an exact inventory of the files changed and hunks introduced reported before any further edits are made. Confidence: 0.6
- Communicates in a mix of Indonesian and English (casual/operational messages in Indonesian, formal scope definitions in English). Confidence: 0.7
- Wants numeric risk scores (e.g., 0–30) accompanied by per-score rationale and an explicit non-objectivity disclaimer, plus a fixed final-verdict vocabulary that must be one of a small allowed set (e.g., COMMISSION_AUTHORITY_CONVERGED / COMMISSION_AUTHORITY_CONTRADICTION_FOUND / PROOF_INCOMPLETE, or PROVEN / PARTIALLY PROVEN / NOT PROVEN / CONFLICT / CONTRADICTED). Confidence: 0.9
- Audit reports must contain an explicit UNKNOWN / UNPROVEN ITEMS section listing everything that could not be proven within the audit's constraints (e.g., no DB access, runtime config values unknown), each item labeled UNKNOWN or UNPROVEN rather than guessed. Confidence: 0.65
- For multi-phase convergence missions, requires a per-phase status report at the end of each phase using a fixed template — VERDICT, CANONICAL_CONTRACT, CHANGES, DELETED, PROTECTED, TESTS (exact commands + exit codes), ACCOUNTING_PROOF, RESIDUE_STATUS, FILES_CHANGED, DATABASE_CHANGED, MIGRATIONS_CHANGED, REGRESSION, FINAL_STOP — not only a final report. Confidence: 0.8
- For broad authority-convergence audits, requires a fixed 21-section final envelope with recognizable headers and nothing outside it — EXECUTIVE VERDICT / MASTER AUTHORITY MAP / WRITER AUTHORITY MATRIX / READER AUTHORITY MATRIX / CALCULATION AUTHORITY MATRIX / API-MOBILE CONTRACT MATRIX / EVENT-OUTBOX MATRIX / CACHE AUTHORITY MATRIX / ZOMBIE-LEGACY-RESIDUE MATRIX / CONTRADICTION MATRIX / STATE-PROOF MATRIX / CLEANUP-READINESS MATRIX / PRIORITY MAP / OWNER DECISIONS REQUIRED / PROTECTED PARALLEL BOUNDARIES / WHAT IS HEALTHY / WHAT IS BROKEN / WHAT IS CONFIRMED DUPLICATE AUTHORITY / WHAT IS CONFIRMED ZOMBIE-RESIDUE / WHAT IS STILL NOT PROVEN / NEXT AUDIT TARGET. Confidence: 0.7
- Never claims convergence/success merely because code compiles or a focused test passes: a passing test that encodes a rejected contract is not evidence, and completion must be proven against the full locked contract (canonical snapshot, buyer cash excludes commission, escrow = PD+S, PD denominators, clearing never over-debited, no dead-field authority, residue clean by semantic search). Confidence: 0.85
- Audit reports structure each conclusion through a mandated evidence chain — FACT → AUTHORITY → DURABLE STATE → CURRENT READER/WRITER → STATIC PROOF → RUNTIME PROOF → VERDICT — and enforce per-conclusion verdicts (one of PROVEN / PARTIALLY PROVEN / NOT PROVEN / CONFLICT / CONTRADICTED per section). "No caller", "test passes", and "code exists" are explicitly rejected as sufficient authority proof; runtime proof is never inferred from tests. Confidence: 0.8
- Wants a separation of report dimensions that distinguishes "implemented but runtime unproven" from "architecturally broken", "confirmed residue", "confirmed duplicate authority", and "business requirement itself unproven" — these are kept as distinct conclusions, never lumped together, and "runtime not proven" alone is never escalated to a P1 defect. Confidence: 0.75
- Bounded cleanup stages require a fixed final report: pre-cleanup residue inventory, proof of deadness for each deleted mechanism, exact files changed, routes/DTOs/services/validators removed, tests/docs/comments updated, canonical-behavior regression proof, tests run with exact results, flutter analyze / go vet outcomes, final symbol/caller audit, baseline (pre-existing, not caused-by-the-change) failures separated from regressions, remaining open issues, out-of-scope list, and a cleanup verdict. Confidence: 0.75
- Audit test-coverage sections classify every existing test into one of canonical/current, stale/divergent, missing, or unrelated (with an explicit MISSING designation for areas with zero dedicated tests) rather than a flat inventory. Confidence: 0.6
- Demands ambiguous runtime/behavior terms (e.g., "reload", "retry", "automatic reload") be decomposed into the distinct technical mechanisms they could denote — HTTP request retry vs app restart vs router redirect vs provider rebuild vs hot reload — and each named precisely; these mechanisms are never treated as equivalent or conflated. Confidence: 0.75
- Interrupted-session recovery reports must answer a fixed set of questions and then end the session: did the prior session actually change files, exact files changed, exact symbols/literals already changed, exact unfinished work, whether the filesystem is safe to continue, and the recommended safest next step — delivered as a report with STOP (no further edits made). Confidence: 0.85
- Read-only convergence-audit reports follow a fixed structure: candidate findings (problem, factual evidence, affected surfaces, authority currently used, duplicate/zombie evidence, user impact, development impact, estimated bounded scope, risk, runtime-proof feasibility), a single recommended next stage with rationale, the proposed bounded stage (what will be changed / what will NOT be touched, expected canonical behavior, cleanup boundary, required proof), business decisions required or an explicit none, parallel-boundary verification, and a STOP section confirming the working tree is unchanged. For staged read-only audits, the report must follow the owner's 15-section template — VERDICT, AUDIT SCOPE, BUSINESS TRUTHS USED, SURFACES AUDITED, FINDINGS, AUTHORITY MAP, DUPLICATE/ZOMBIE MAP, CONTRADICTIONS/BUSINESS DECISIONS REQUIRED, PRIORITIZED CANDIDATES, RECOMMENDED NEXT STAGE, EXACT BOUNDED SCOPE, EXPLICIT OUT-OF-SCOPE, BASELINE FAILURES, RISKS, STOPPING POINT — and must explicitly distinguish FACT from INFERENCE throughout the report. Confidence: 0.85
- Bounded implementation/convergence stages require a fixed final report: verdict, business truth implemented, canonical authorities, consumer inventory, actual files changed and deleted, tests added, exact test commands with results, flutter analyze / go vet result, remaining baseline failures separated from regressions, final duplicate/residue audit, parallel-boundary (e.g., Commerce) confirmation, open issues/ambiguities, and STOP. Confidence: 0.7
- Interrupted-session repair reports follow a fixed template: exact corruption found per file, exact repairs made, explicit confirmation that valid in-flight rename work was preserved, exact files changed, build/test results, pre-existing failures separated from regressions, current stage completion status, explicit confirmation that later stages (migration/mobile) were NOT started, remaining blockers, and STOP. Confidence: 0.75
