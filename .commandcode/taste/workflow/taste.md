# Workflow Preferences

- Prefers read-only, evidence-only audits before any implementation; audit scopes explicitly forbid modifying source, tests, schema, or migrations, and permit creating at most the single explicitly-designated audit report artifact (e.g., the named audit .md file) — nothing else. Confidence: 0.95
- Audit passes must be purely discovery-oriented: never "fix" discovered issues, never add compatibility logic, never choose a business model merely to make current code pass, and label any inferred business truth explicitly as inference rather than fact. Confidence: 0.9
- Refuses HTTP 201 / unit-test PASS / integration-test PASS / compile-success as runtime proof of a feature: proof requires tracing the full convergence chain (request → durable state → subsequent read → mobile state → UI convergence); a success response or green test is explicitly not evidence of convergence. Confidence: 0.85
- Caller absence is evidence, not proof: does not classify code/tests as dead merely because a caller/reference search returns zero matches; semantic role, dependency status, and compilation-impact (does it break the build?) are verified before labeling anything a zombie/residue. Confidence: 0.8
- Determines canonicality/authority only from evidence (the actual table/SQL/route/DI wiring, real writers and readers), never from naming or inferred role: "do not decide canonicality from naming" — a similarly named repository/column/field is not canonical (or duplicate/legacy) merely because of its name; the physical table it touches and its reachable production writers/readers decide. Confidence: 0.85
- Audits must not conflate UX feedback with security/business authority: the layer that only displays or pre-filters validation (UI widgets, inline screen validators) is separated from the layer that actually enforces acceptance/rejection (Firebase/backend), and each responsibility is attributed to its own layer — "do not conflate UX feedback with security authority." Confidence: 0.75
- Applies a cleanup-readiness gate before classifying anything as READY FOR CLEANUP: a candidate is READY only when (1) canonical authority is proven, (2) lifecycle is proven, (3) all production callers are mapped, (4) a canonical replacement is proven, (5) no schema/API/event dependency remains, and (6) the regression surface is known; otherwise it is NOT READY and the specific missing precondition must be stated. Confidence: 0.8
- Independently verifies high-consequence claims from sub-agents/explore tools directly (reading files, greps, compile checks) rather than trusting them; consequential findings (e.g., "X is a dead/compile-broken module") are re-verified first-hand before being reported. Confidence: 0.75
- Treats observed/runtime values as unproven until their source and authority are traced in code; refuses to assume observed values are semantically correct merely because they were seen, and does not assume focused test numbers are representative unless the source proves it. Confidence: 0.9
- Sequences audit work strictly: the discovery/authority map and full classification must be complete before any implementation proposal is made ("do not propose implementation until the authority map is complete"). Confidence: 0.85
- Prefers audits to verify code against the user's explicit list of locked business truths/domain invariants (formulas, denominators, scope rules) rather than inferring truth from code alone. Confidence: 0.75
- Discovery must be exhaustive beyond keyword grep: inspect semantically equivalent calculations and representations, not just obvious keyword matches. Confidence: 0.7
- Audits must trace the complete lifecycle end-to-end for each audited field/value — canonical producer → persistence → hydration → every downstream consumer (payment, refund, release, reconciliation/verifier) — proving that it is actually produced, persisted, hydrated, and consumed, rather than auditing isolated components in pieces. Confidence: 0.75
- Distinguishes "different values" from "contradictions": differing numeric values (e.g., a total vs. an event delta) must be proven semantically related or contradictory by tracing exact source authority — never declared contradictory merely because the numbers differ, and never chosen between by intuition; the business contract and locked decisions decide. Confidence: 0.85
- Treats the current filesystem as the sole implementation truth; git/GitHub history is explicitly NOT implementation authority for decisions. Confidence: 0.9
- Forbids git rollback/restore commands (checkout, restore, reset, clean, stash, cherry-pick, revert); repairs must be written forward on the current filesystem, and reversing one's own mistakes should use the edit/session history of the exact hunks introduced — not git. Confidence: 0.9
- Demands narrow, bounded work slices with explicit protected/out-of-scope lists, forbidden actions, and stop conditions; strongly rejects cross-domain scope creep (e.g., finance/payment/coins/refund code must not be touched during content/share work). Confidence: 0.9
- Never skips, trims, or "neutralizes" tests to make a package compile; newly skipped safety tests are unacceptable — fix root causes or report the blocker. Confidence: 0.8
- Tests that pin a canonical contract are treated as evidence of intended design even when they fail to compile against the current tree; when production lacks the fields/methods the canonical design requires, repair production AND the test contract in a bounded way — never delete a test merely because it currently fails. Confidence: 0.85
- Tests that describe a design the owner explicitly rejected (e.g., a delete-media endpoint) are replaced with a decision-lock test asserting the rejected artifact is ABSENT (route/logic not registered), preserving a documented decision trace — never silently deleted and never left as a t.Skip (skip does not fix compilation of the test body). Confidence: 0.7
- When a contract test pins both in-scope and out-of-scope (protected-domain, e.g., Commerce) features, the out-of-scope assertions are removed and only in-scope assertions retained — the protected-domain feature is never implemented merely to satisfy the test. Confidence: 0.7
- When a failing test encodes the locked canonical contract and the production code retains the rejected residue (e.g., a local reserved-name list contradicting the backend authority), the test is evidence against the residue: fix the production code to satisfy the contract and keep the test intact — never "fix" the test or classify it as stale. Confidence: 0.7
- When a focused task is blocked by unrelated package-wide compile/test debt, prefers isolated explicit-file test invocations and does not treat unrelated package-wide debt as an acceptance gate. Confidence: 0.7
- Prefers forward-only, surgical fixes; when reversing accidental changes, do not "modernize" or independently repair unrelated stale APIs. Confidence: 0.7
- Prefers documentation to be authoritative: docs extracted from the codebase are revised until final, and afterwards the codebase must follow the docs. Confidence: 0.7
- Wants full-suite verification run in a clean window (no other processes mutating the shared test database) with the complete package — no selective test filtering. Confidence: 0.6
- Cleanup doctrine for rejected implementations: anything proven to represent a rejected model must be deleted, not deprecated and never kept "for compatibility" — no dead functions, comments, fixtures, tests, aliases, or documentation left behind that could resurrect it (enabled by zero-production-data / no-backward-compatibility policy); residue must be proven clean by semantic search, not assumed. Confidence: 0.95
- Before modifying code that depends on a data field, trace the exact data path and verify the canonical field is genuinely available; if unavailable, STOP and report PROOF_INCOMPLETE rather than inventing a substitute denominator/value. Confidence: 0.85
- Stop-and-escalate rule: if implementation reveals a new contradiction in business/accounting authority outside the authorized scope, STOP and report it as a blocker for owner/architecture decision — never solve the newly-discovered contradiction opportunistically. Explicit stop conditions include two genuinely incompatible business interpretations, a missing owner decision, a ledger movement with undefined funding source, a canonical formula contradicting an actual ledger invariant, uncertainty whether an artifact is stale or intended, and a test whose expectation contradicts the locked canonical contract — do not guess; STOP if the existing code does not establish the funding contract. Confidence: 0.95
- Treats the mere existence of an artifact (untracked test, migration, cmd tool) as NO evidence of intent: stale residue is not implemented merely because it exists, APIs are never resurrected just to make stale tests compile, and canonical production code is never adapted to satisfy tests that encode a rejected contract — stale-layer status must be proven by a separate audit establishing an independent canonical requirement. Confidence: 0.8
- Validation ordering for implementation changes: run the focused package tests first, then directly affected package tests, then broader related packages, then go vet for the affected packages. Confidence: 0.8
- Frames implementation tasks as "executor, not architect": implement exactly the locked spec/scope, do not redesign, invent new formulas, or add new authorities during execution — architectural decisions belong to the audit/owner, not the implementation pass. Confidence: 0.7
- Audits must validate authority claims against actual cash flow, not just code-level formulas: reconcile pricing-token totals, actual payment cash, gateway clearing inflow/outflow, escrow, and commission, and prove whether each claimed identity (e.g., EscrowAmount = P+S+C) is economically possible under the real payment flow. Confidence: 0.75
- Treats prior audit conclusions as correctable: when new evidence (e.g., runtime fixture numbers) disproves an earlier audit's claim, explicitly revises that finding in the new report rather than defending it — evidence trumps prior conclusions, including one's own. Confidence: 0.65
- When deciding whether a data field is a genuinely required snapshot authority or should be replaced by another canonical representation, decides on proof of production writes/reads and cash-flow evidence — never on convenience. Confidence: 0.7
- Treats unrelated parallel work, pre-existing build breaks, and out-of-scope domains as inviolable: never reverts or independently repairs them as part of the task. Confidence: 0.85
- Before deleting any artifact as "stale residue" during destructive cleanup, verify its semantic role and dependency status (e.g., whether it is a shared test harness other tracked tests depend on) and its tracked/untracked status — surface-level rejected assertions alone are not sufficient justification, and a file not on the owner's authorized delete list is protected. Confidence: 0.85
- Tracked files not enumerated in the owner's authorized change/delete list are treated as protected even when their content encodes a rejected contract; updating or deleting them requires explicit owner authorization — STOP and report rather than edit unilaterally. Confidence: 0.8
- When an accidental deletion removes shared test infrastructure, recover it from a faithful backup copy of the exact file; never speculatively reconstruct large shared harnesses from fragments — if faithful recovery is impossible, STOP and report rather than invent test infrastructure. Confidence: 0.75
- A kill list's symbols are contract-specific, not literal symbol bans: before deleting a reject-contract artifact that shares a name/pattern with a kill-list entry, verify its actual consumers — shared/generic helpers legitimately used by unrelated domains (e.g., a reusable pagination envelope consumed by the follow domain) are NOT residue and must be kept even though they match the kill list; only artifacts whose consumers are exclusively the rejected contract are deleted. Confidence: 0.8
- Distinguishes "static cause candidate" from "runtime-proven root cause": refuses to claim a runtime root cause for an observed defect (e.g., "empty feed caused by mobile provider lifecycle") without runtime evidence; a plausible hypothesis is explicitly labeled a static candidate / NOT PROVEN and never promoted to a defect verdict. Confidence: 0.85
- Applies a "NOT PROVEN AS DEFECT" standard to gap/missing artifacts (missing lifecycle events, absent consumers, absent features): an absence is treated as a gap, not a defect, unless there is evidence that a current consumer/business workflow actually requires it — explicitly answer "is there evidence a current workflow requires this event/artifact?" before labeling its absence a defect. Confidence: 0.85
- When a task designates protected/prohibited parallel domains (e.g., finance/payment/coins/refund/order), reports a Social/current-domain touch point on a protected domain only as PARALLEL / PROVENANCE UNKNOWN and never inspects or judges the protected domain's internal authority. Confidence: 0.85
- Verifies each finding's sub-dimensions separately (persistence writer vs reader, event contract, producer, consumer, DTO-field status, business-model intent — e.g., mention questions A–I answered independently) and makes a determination for each dimension, rather than collapsing everything into one flat conclusion. Confidence: 0.7
- When a tracked test is a mixed artifact (valid coverage plus assertions that encode a rejected model) and the owner authorizes test convergence, surgically convert ONLY the rejected assertions to canonical equivalents while preserving the valid coverage — do not delete the whole test, and never let the rejected assertions drive production. Confidence: 0.65
- Interrupted-session recovery protocol: when resuming work after an interruption, first recover current state (inspect filesystem/worktree and git status) instead of restarting blindly; if the designated report/artifact exists, continue from its last completed section and reuse its verified work rather than repeating expensive searches; cross-check the incomplete artifact's claims against the current filesystem before trusting them; never assume changes visible in git status were caused by the interrupted session; never restore/checkout/reset/revert the filesystem to replace current state; and never create duplicate reports or temporary files. Confidence: 0.9
- Interrupted-session recovery is a read-only verification pass, NOT a resume-to-implement: run only cheap/relevant checks to determine state (dry build, vet, targeted greps) — no new implementation, no zombie/dead-code cleanup, no commit or push — and STOP after delivering the recovery report. Confidence: 0.9
- When resuming an interrupted bulk rename, verifies whether the previous session's last stated action (e.g., "applying targeted replacements") actually executed by grepping the current filesystem for the exact target symbols/literals — never trusting the session's last log line — and classifies each area as done / not-done / corrupt-half-done before proposing next steps. Confidence: 0.85
- Prefers one canonical vocabulary/terminology for each business concept, applied consistently across domain, schema, API/wire, DTO, mobile, and tests; divergent legacy synonyms for the same concept (e.g., listing / fixed_price_sale → for_sale) are unified to a single name, production inconsistencies in the wire (e.g., feed emits one term while search emits another for the same surface) are identified and converged, and old legacy terms are fail-closed rather than silently accepted. Confidence: 0.75
- Historical migrations are canonical and never rewritten for cosmetics; schema vocabulary changes must be delivered as a new migration (never editing prior migration files), except the new migration may drop dead enums/values and backfill renamed enum values. Confidence: 0.8
- For legacy/zombie cleanup stages, mandates an audit-first residue protocol: before deleting anything, run a per-candidate audit that locates the definition, every caller, every consumer, route registration, DTO/request/response usage, tests, and docs/comments; classify each candidate as canonical, required establishment logic, test-only residue, or truly dead; and delete only what is proven dead — never delete first and audit later, never assume a listed cleanup target is dead, and never treat a candidate list as a verdict. Confidence: 0.9
- Implementation stages must audit all production callers BEFORE editing any validator: every validator is inventoried (definition, callers, surface, actual rules, canonical/duplicate/legacy/specialized classification) and only then converged or preserved as a legitimate wrapper. Confidence: 0.75
- When a stage brief supplies known/prior audit findings, reconfirms each finding against the current filesystem before acting — prior findings are never trusted blindly, and caller/consumer reality is re-verified first-hand rather than inherited from the brief. Confidence: 0.8
- Declares a stage COMPLETE only after a final audit proves: exactly one active authority/engine remains, no active consumer carries its own parallel algorithm, no rejected-residue constants/terms remain (verified by repo-wide symbol/caller grep), policy/validity authority is untouched and still the sole gate, and dead code within stage scope is removed. Confidence: 0.7
- During scoped cleanup, refuses to delete a zombie writer/component when it has live consumers through a provider chain or is pinned by an existing (even baseline-failing) test; the cleanup is limited to proven-dead helpers with zero callers (e.g., a removed `getCoverPhotoUrl`/`deleteCoverPhoto`), while deeper zombie writers are preserved and documented as open issues for an owner decision. Confidence: 0.7
- A production consumer that enforces a policy on a surface where it does not belong (e.g., login applying registration min-length policy and blocking existing shorter credentials) is an in-scope convergence bug to fix with caller evidence — not a pre-existing issue to leave alone. Confidence: 0.75
- Cleanup after convergence is strictly scoped: only policy residue proven dead (zero callers after the change) is removed, while items the owner explicitly protected (e.g., a legacy parallel password input) are preserved and carried forward as named remaining residue for later stages. Confidence: 0.7
- Treats the PRD/audit brief as a hypothesis, not absolute business truth: when code, runtime evidence, or existing behavior contradicts the brief, STOP and report the contradiction — never invent or guess a business rule; business truth is established by the OWNER through discussion, not inferred by the executor from the PRD. Confidence: 0.8
- Never fixes what has not been proven: a fix (e.g., hiding an error screen to mask a symptom) requires an evidence-based root cause first; the mandated sequence is OBSERVE → MAP → PROVE ROOT CAUSE → DECIDE BUSINESS/UX IF NEEDED → IMPLEMENT SMALL → RUNTIME PROOF → SCOPED CLEANUP → FINAL PROOF, and speculative fixes/compatibility shims are forbidden. Confidence: 0.9
- Records the working-tree baseline (git status + git diff --stat) before starting a read-only audit and treats all pre-existing dirty changes as inviolable baseline rather than the session's work; the final report must confirm no unrelated files were changed and only the designated report artifact was created. Confidence: 0.75
- Recommends implementation as the smallest safe sequence of bounded stages (e.g., Stage 3B-A → 3B-E), each stage ending with its own runtime proof, and keeps cleanup out of implementation stages (a separate later scoped stage). Confidence: 0.7
- Prefers real runtime/integration proof when the environment permits; when runtime reproduction is impossible, states this explicitly and leaves the runtime dimension as pending owner-side verification rather than claiming full proof from unit/widget tests alone. Confidence: 0.65
- No DB reset unless explicitly requested by the owner; a dirty/broken baseline is never "fixed" by resetting or mutating database state without explicit authorization. Confidence: 0.7
- Next-stage candidate discovery must be a fresh, factual search of the current codebase — never anchored on previous owner findings or prior-stage assumptions; candidates are found by directly searching for duplicate authorities, dead/zombie paths, and contract inconsistencies in the code. Confidence: 0.75
- Selects the next bounded task by highest leverage and lowest conflict risk (user-visible or development-correctness impact, reduced repeated-bug surface, narrow/safe scope, independence from parallel-chat domains, canonicalization suitability), not by bug count — the goal is the next small task that makes the app more proper while accelerating development; candidate ranking is explicit: (1) user-visible impact, (2) regression risk if left unresolved, (3) number of divergent consumers of the same business rule, (4) strength of the existing canonical authority, (5) cleanup safety, (6) testability / deterministic proof, (7) scope isolation — preferring surfaces where the same business rule is implemented differently in multiple places under one clear canonical authority, and never optimizing merely for "easy P2/P3"; exactly ONE top next stage is recommended, never a ranked list to pick from. Confidence: 0.85
- Bounded stages introduce no new tools, packages, or architectural layers; they reuse existing mechanisms and authorities unless a requirement provably cannot be met otherwise. Confidence: 0.75
- Audits existing helper/organization conventions before accepting file names or locations suggested in a task brief; suggested names are hypotheses to verify against the codebase's actual conventions (e.g., canonical helpers live in shared/helpers following the CanonicalUsernameValidator pattern), never adopted blindly. Confidence: 0.6
- Interrupted-session repair phase (after the read-only recovery audit): repair ONLY the corruption the crash caused, preserve all legitimate in-flight rename work (never revert valid renames merely because the file is damaged), do not start new stages (migration/mobile/unrelated cleanup), and prove recovery with gofmt + go build + go vet on affected packages + focused tests before reporting; failures outside the repaired files are reported as pre-existing baseline, not regressions. Confidence: 0.85
- During dead-code cleanup, a component that hosts live canonical consumers is preserved as an ACTIVE seam even when it also contains a dead hook: the cleanup unit is the proven-dead hook/field/param excised from within (e.g., ValidationService kept as the thin canonical delegation seam with only its dead anti-circumvention/content-moderation hook removed), never the whole component — a component is not deleted merely because it is the file that happened to hold dead code. Confidence: 0.7
- Vocabulary-convergence residue audits classify EVERY remaining occurrence of a legacy term into explicit categories before editing — LIVE CANONICAL (must rename), LIVE NON-COMMERCE/unrelated (preserve), TEST EXPECTATION (update if it asserts current canonical behavior), COMMENT/DOC (update if it describes current vocabulary), HISTORICAL/MIGRATION (preserve for the later schema stage), DEAD/ZOMBIE (remove if safely bounded to the stage) — and inspect each occurrence rather than relying on raw grep counts; a legacy term is never blindly replaced globally because it legitimately occurs in unrelated domains (e.g., "listing" as enumeration) and in historical migration SQL. Confidence: 0.8
- During vocabulary convergence, fail-closed legacy-rejection tests (tests that lock rejection of the old term, e.g., asserting `listing_id` is rejected) are preserved intentionally and their legacy literals are not renamed; only test expectations that assert current canonical behavior are updated to the new vocabulary. Confidence: 0.65
- Renaming event strings/domain vocabulary audits all producers, consumers, registry entries, tests, and comments of the exact symbols BEFORE editing and updates them in lockstep (producers/registry/tests changed together in one pass); dead stub events are still converged to canonical vocabulary without creating compatibility aliases. Confidence: 0.75
- Before coding a bounded implementation stage, presents a short pre-implementation checkpoint: exact files/surfaces to be touched, the authorities to be used, what is intentionally NOT touched (out-of-scope), and risks/STOP conditions — coding begins only after this checkpoint is laid out. Confidence: 0.75
- Multi-substage implementation runs on a report-and-wait gate: after each bounded substage completes, results are reported and the assistant stops for the next instruction rather than autonomously proceeding through all substages. Confidence: 0.7
- When the task brief designates a repository/entity method as "for test exposure" only, prefers not to add a public test-only API to production classes; the wire behavior is proven instead through serialization/DTO tests and existing datasource-recording integration tests. Confidence: 0.6
- In read-only audits, when a required backend capability is found absent (e.g., DB column exists but no Go entity/SQL/API touches it, or no delete endpoint), the audit does NOT fill the gap or pick a single design — it reports the required architecture choices as explicit owner decision points (concrete options, a recommended option, and per-option stop conditions) and stops there; no schema/API/endpoint/business rule is invented to complete the missing layer during the audit. Confidence: 0.75
- When briefing an audit, expects the required report structure and the exact forbidden actions (no production code, no schema, no tests) to be enumerated UP FRONT in the brief itself — including the mandatory report sections (current factual flow, existing canonical authority, exact gap/root cause, affected files, reusable existing infrastructure, schema/API status, consumers, tests, recommended bounded implementation plan, STOP conditions/business decisions) — and the audit must follow that enumerated structure, not improvise one. Confidence: 0.7
- When a stage brief authorizes the full pipeline in one message (audit → implement → focused tests → scoped cleanup → final proof → report) and keys the stop condition to "STOP after audit only if a new business decision surfaces; otherwise proceed bounded", the executor runs the whole pipeline continuously in one session — a clean audit (no new business decision) is a green light to proceed, not a checkpoint requiring a new instruction; only a newly-surfaced business decision or an out-of-scope blocker halts the run. Confidence: 0.65
