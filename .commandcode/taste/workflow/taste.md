# Workflow Preferences

- Once the Owner has locked the canonical business truth for a concern and declared it final/non-negotiable, the executor proceeds on that decision and never re-litigates or re-asks it ("Owner has already decided the business truth. Do not ask the owner again whether default should be X or Y") — the Owner's decision is the single business truth and convergence work executes against it. Confidence: 0.8
- A convergence/purge implementation is never declared COMPLETE merely because tests pass: it ends with a MANDATORY second-pass audit read from the final filesystem, framed adversarially as "if I were a fresh agent with no conversation context, could I read this repository and conclude the OLD default?" — a fixed question set (can a constructor still produce the old default when the caller omits the mode; does any env example/comment still teach the old default as opt-in; is there a second raw config read for the same concern; do tests preserving the old semantics survive; is there an alternate bootstrap constructing a different policy; does unset config have exactly one answer repo-wide; can malformed config silently produce a business mode; does the active gate actually receive the canonical default; are all affected channels suppressed) — and completion requires proof that no artifact in the active or future-reachable codebase can teach or construct the old default world. Confidence: 0.75
- Authority-convergence tasks purge the whole semantic family, not just the reported bug: fixing the parser alone is insufficient — the competing default is eliminated from the type/constructor default, the boot-time inline env parser, the docs/comments, the `.env` and `.env.example` templates, and the tests in the same pass, so exactly one semantic model remains. Confidence: 0.7

- Applies an explicit authority-precedence hierarchy when briefs, docs, runtime, and code conflict: Owner explicit decision > Runtime factual behavior > Filesystem implementation > old documents/PRD/reports > Git history — filesystem is the technical authority to audit and git history is never consulted as design authority, old docs/legacy implementations are never revived merely because they were found, and legacy flows are not kept for compatibility once canonical authority is proven. Confidence: 0.8
- Lookalike-concern authority audits never assume architectural uniformity: sibling concerns that appear to share one design (e.g., Feed / Content Detail / Search Content evaluator modes) are each audited independently — own authority chain, own environment matrix, own construction/reachability trace — and then compared property-by-property in a mandatory matrix (ENV variable / config field / runtime default / documentation default / invalid behavior / normalization owner / final mode owner / handler gate / shadow-runner role / competing authority) answering whether there is genuinely ONE architecture or several lookalike designs; concerns are never equated merely because their names or shapes match ("jangan menyamakan mereka hanya karena namanya sama"), and a divergence found in only one of them (e.g., a case/whitespace-sensitive normalizer behind a case-insensitive validator) is reported as its own finding rather than smoothed into the shared picture. Confidence: 0.7
- Cross-domain legacy-cleanup blocker rule: a domain boundary is NEVER a valid excuse to leave a legacy authority alive when a consumer in that other domain factually blocks the cleanup — a previous report labeling that consumer "out-of-scope" is not an eternal shield and is revoked the moment cleanup requires it; the foreign-domain consumer becomes part of the migration work, and the dependency chain is followed across domain boundaries (auth → auction → user → profile → core) until the factual authority is clear — folder boundaries are not boundaries of correctness. Confidence: 0.8
- Cross-domain legacy-refactor pass runs on a READ → TRACE → PROVE → DECIDE protocol before any edit: do not edit/refactor/create new providers/interfaces/delete-on-name-looks; first read the actual filesystem, map EVERY producer, map EVERY consumer, trace each consumer's runtime/business purpose, determine the factual authority, and only implement after the authority is proven — verified against the filesystem, never trusting a prior report's claim (re-prove e.g. "Auction consumes X" with first-hand grep/read before touching code). Confidence: 0.75
- Cross-domain authority decision uses an explicit four-way verdict per dependency — KEEP (only when it has a proven canonical runtime purpose) / MIGRATE (consumer needs the data but the legacy dependency is not the right authority → move the consumer to the canonical authority) / PURGE (canonical replacement is factual and ALL consumers migrated or removed → hard-purge producer + interface + implementation + provider + exports + helpers + stale tests/comments keeping it alive) / UNRESOLVED (authority not provable → NEVER implement as if correct; expand the audit). Confidence: 0.7
- Authentication/domain-audit fix planning is per-defect and bounded, never a single mega-refactor: each fix plan states exactly one defect → the exact authority to preserve → the exact authority to remove → the files likely affected → the tests required → the runtime gate required; nothing is implemented during the audit phase and fixes wait for an explicit next decision. Confidence: 0.7
- When using a shell tool whose working directory persists across calls (e.g., PowerShell keeping cwd from an earlier command that cd'd into a subdir such as `backend/`), repo-relative existence/git checks silently run from the wrong directory and can produce misleading ABSENT/EMPTY/clean results (a tracked file falsely reported absent on disk, `git ls-files` falsely empty); before any repo-relative filesystem or git verification, explicitly reset/confirm the working directory (Set-Location to the repo root, verify with Get-Location), and treat a surprising ABSENT or clean result as a possible cwd artifact to re-verify from the correct root before concluding the repository state actually changed. Confidence: 0.7
- Repository markdown retention policy (total-markdown-purge doctrine): every file exactly named `README.md` — wherever it lives (root, backend/, apps/, scripts/, even nested `docs/` folders) — and every `*.md` located directly at the repository root are KEPT by explicit repository rule, regardless of how stale or aspirational their content is; only nested non-README `.md` files are purge candidates, and root-level `.md` files are never deleted merely because they are not READMEs. README preservation is a file-level rule and is never treated as endorsement of README content as design authority: stale narrative inside a kept README is tolerated, and only links/references that point to files actually purged are straightened or removed — the README itself is never deleted, emptied, renamed, or moved to satisfy convergence. Purge work never recreates, renames, archives, backs up, or relocates legacy markdown and never creates placeholder/compatibility/`docs/legacy`/`docs/archive` documents. Confidence: 0.7
- Missing-artifact canonicality audits decide restore purely on current active consumers, never on git history: an artifact's prior existence in git is forensic provenance evidence only and never implies "pernah ada → harus dikembalikan"; references are classified by type (RUNTIME / CI / BUILD / DEPLOYMENT / TOOLING vs DOCUMENTATION / COMMENT / HISTORICAL_METADATA), with comments, README citations, aspirational TODOs, legacy scripts, and dead deployment workflows explicitly non-active; no dummy artifacts are created and nothing is restored merely to make a CI guard green. Confidence: 0.75
- A CI workflow/guard authored while an artifact existed and never updated after that artifact was intentionally deleted is broken-by-construction (BROKEN_ACTIVE_WORKFLOW), not a restore trigger: the guard-vs-cleanup contradiction is an owner decision between forward-correcting the guard and authoring new canonical docs, and while undecided it triggers a DEEPER_AUDIT_REQUIRED stop — the deleted artifact is never restored to satisfy the stale guard. Confidence: 0.7
- When auditing whether a third-party service is still used, separates general service usage from each specific component/surface and proves each separately: e.g., Firebase being live for Auth/FCM/analytics via client configs never proves Firebase Functions is an active deployment surface — deployment config (firebase.json, functions/) and actual call sites are verified before labeling anything a live or dead deployment. Confidence: 0.7
- Script/operational-tool audits treat OS-differentiated pairs of the same semantics (e.g., `db_backup.sh` vs `db_backup.ps1`, `test.sh` vs `test.ps1`, `db_restore.sh` vs `db_restore.ps1`) as PLATFORM_VARIANTs, never as duplicates to purge — OS difference is explicitly not duplication, and platform-variant status is verified by reading script contents to confirm same semantics before classifying. Confidence: 0.8
- Scripts with real, documented function but only manual invocation (no CI workflow, git hook, VS Code task, or Makefile consumer) are classified ACTIVE_MANUAL_TOOL and preserved — "no automated consumer" alone is never orphan/residue evidence ("jangan salah mengklasifikasikan sebagai orphan hanya karena manual"); a script is PROVABLE_UNUSED only with no runtime consumer AND no CI consumer AND no tooling consumer AND no structural contract. Confidence: 0.8
- Distinguishes BROKEN from PROVABLE_UNUSED for scripts: a script that retains a real operational function but depends on missing files/paths/compose overrides or hardcoded out-of-date paths is BROKEN — a smallest-correction candidate, never a purge candidate; PROVABLE_UNUSED (purge) requires the full four-proof absence standard, and UNKNOWN is used when evidence is insufficient rather than forcing a purge candidate. Confidence: 0.65

- Structural-scaffold/empty-directory attachment audits classify each scoped path's factual contents (empty / .gitkeep only / README only / configuration / runtime artifact / tool output / source / other) and treat emptiness as NO evidence of removability and README existence as NO evidence of active structure: a purge candidate requires proof of no active runtime consumer + no CI consumer + no tooling consumer + no producer requiring a pre-existing path + no structural contract, where the structural contract distinguishes a command expecting the path to pre-exist, Git preserving an otherwise-empty required location, and tooling that dynamically creates the path when needed (e.g., a backup script's own `mkdir -p` output dir); actual output locations are found where producers write (gitignore-declared dirs, script mkdir), never assumed from where scaffold dirs sit, and `.gitkeep` files are never removed during a read-only audit. Confidence: 0.7
- Destructive/data migrations are authored only against the actual current schema and migration history: inspect the real schema, migration files, and all consumers first, remove consumers before migrating, and never build a destructive migration or data mapping from assumption; a migration step whose mapping cannot be proven from the current filesystem is STOP-and-report blocker material, and clean replay from the canonical baseline is a required verification. Confidence: 0.7
- Cross-codebase phases keep each surface hard-bounded: a backend-only phase never modifies mobile code, and backend contract changes are written as an explicit contract-delta section in the phase report so the later mobile phase consumes the actual canonical contract. Confidence: 0.6
- An out-of-scope client/surface (e.g., mobile) that still consumes a mechanism whose schema the in-scope layer already dropped does NOT veto in-scope cleanup: the mechanism is removed fully from the in-scope layer (no resurrected columns, no compatibility columns/methods, no partial derivation to keep the client working), and the out-of-scope dependency is documented in the report as a separate blocker/task for that surface — an owner-confirmed choice of full removal over restoring the removed schema. Confidence: 0.65
- Prefers read-only, evidence-only audits before any implementation; audit scopes explicitly forbid modifying source, tests, schema, or migrations, and permit creating at most the single explicitly-designated audit report artifact (e.g., the named audit .md file) — nothing else. Confidence: 0.95
- Audit passes must be purely discovery-oriented: never "fix" discovered issues, never add compatibility logic, never choose a business model merely to make current code pass, and label any inferred business truth explicitly as inference rather than fact. Confidence: 0.9
- Refuses HTTP 201 / unit-test PASS / integration-test PASS / compile-success as runtime proof of a feature: proof requires tracing the full convergence chain (request → durable state → subsequent read → mobile state → UI convergence); a success response or green test is explicitly not evidence of convergence. Confidence: 0.85
- Caller absence is evidence, not proof: does not classify code/tests as dead merely because a caller/reference search returns zero matches; semantic role, dependency status, and compilation-impact (does it break the build?) are verified before labeling anything a zombie/residue. Confidence: 0.8
- Consumer-graph evidence rule: self-references (an artifact referenced only by itself or from within its own consumer chain) are never proof the artifact is required — consumer graph evidence is split into executable consumer / structural consumer / documentation-only reference / comment-only reference / self-reference, and only executable or structural consumers establish a factual need. Confidence: 0.6
- Repository-orphan/attachment audits treat coexistence in the same Git repository as NOT attachment: attachment must be proven by tracing actual references through build/runtime/test/CI/scripts/tooling/docs/package/workspace surfaces; generic string hits (e.g., a shared port number) are rejected as evidence, and reference DIRECTION is checked — a Labuda-owned config string (CORS origin, FRONTEND_URL) defaulting to `localhost:3000` points from Labuda to a port, not into the demo's files, so it is an inert shared value, not a dependency; a purge verdict requires positive absence evidence across every enumerated inspected surface, and an unprovable status is reported UNCLEAR/UNPROVEN, never inferred from appearance. Confidence: 0.7
- Chooses early cleanup-program steps to yield a clearly-safe first purge candidate and treats a bounded purge as a deliberate probe: if something breaks after the purge, the break is read as revealing a previously hidden dependency and is fixed forward — legacy artifacts are never revived merely because a purge surfaced a break. Confidence: 0.7
- Determines canonicality/authority only from evidence (the actual table/SQL/route/DI wiring, real writers and readers), never from naming or inferred role: "do not decide canonicality from naming" — a similarly named repository/column/field is not canonical (or duplicate/legacy) merely because of its name; the physical table it touches and its reachable production writers/readers decide. Confidence: 0.85
- Audits must not conflate UX feedback with security/business authority: the layer that only displays or pre-filters validation (UI widgets, inline screen validators) is separated from the layer that actually enforces acceptance/rejection (Firebase/backend), and each responsibility is attributed to its own layer — "do not conflate UX feedback with security authority." Confidence: 0.75
- Applies a cleanup-readiness gate before classifying anything as READY FOR CLEANUP: a candidate is READY only when (1) canonical authority is proven, (2) lifecycle is proven, (3) all production callers are mapped, (4) a canonical replacement is proven, (5) no schema/API/event dependency remains, and (6) the regression surface is known; otherwise it is NOT READY and the specific missing precondition must be stated. Confidence: 0.8
- Independently verifies high-consequence claims from sub-agents/explore tools directly (reading files, greps, compile checks) rather than trusting them; consequential findings (e.g., "X is a dead/compile-broken module") are re-verified first-hand before being reported. Confidence: 0.75
- Repository/boundary-mapping passes (the factual phase that precedes any cleanup/convergence decision) classify directories strictly by role — APPLICATION_RUNTIME / APPLICATION_SOURCE / SHARED_SOURCE / TEST / DATABASE / INFRASTRUCTURE / SCRIPT_TOOLING / CONFIGURATION / DOCUMENTATION / GENERATED / UNKNOWN — and forbid value judgments outright: nothing is labeled canonical/legacy/obsolete/dead/duplicate/wrong during mapping, existence is only a factual observation, and canonical business authority is never inferred from repository structure or naming. Confidence: 0.8
- For large multi-surface codebases, topology/entry-point mapping inspects each major area progressively (area root → immediate children → build/runtime metadata → entry points → major internal module boundaries → test locations → configuration) rather than relying on one shallow recursive directory listing, and key entry points/claimed facts are verified first-hand before the final report. Confidence: 0.75
- Treats observed/runtime values as unproven until their source and authority are traced in code; refuses to assume observed values are semantically correct merely because they were seen, and does not assume focused test numbers are representative unless the source proves it. Confidence: 0.9
- Sequences audit work strictly: the discovery/authority map and full classification must be complete before any implementation proposal is made ("do not propose implementation until the authority map is complete"). Confidence: 0.85
- Prefers audits to verify code against the user's explicit list of locked business truths/domain invariants (formulas, denominators, scope rules) rather than inferring truth from code alone. Confidence: 0.75
- Discovery must be exhaustive beyond keyword grep: inspect semantically equivalent calculations and representations, not just obvious keyword matches. Confidence: 0.7
- Audits must trace the complete lifecycle end-to-end for each audited field/value — canonical producer → persistence → hydration → every downstream consumer (payment, refund, release, reconciliation/verifier) — proving that it is actually produced, persisted, hydrated, and consumed, rather than auditing isolated components in pieces. Confidence: 0.75
- Distinguishes "different values" from "contradictions": differing numeric values (e.g., a total vs. an event delta) must be proven semantically related or contradictory by tracing exact source authority — never declared contradictory merely because the numbers differ, and never chosen between by intuition; the business contract and locked decisions decide. Confidence: 0.85
- Treats the current filesystem as the sole implementation truth; git/GitHub history is explicitly NOT implementation authority for decisions. Confidence: 0.9
- Before touching code, re-reads the repo's working-rules documents first — cara-kerja.md (especially its bottom section) AND PRD.md — and re-verifies target symbols, producers, consumers, imports, and barrel exports against the current filesystem — documents, audit reports, and git history are not implementation authority, and when a prior audit conflicts with the current filesystem the correct action is STOP + report the divergence, never forcing the old audit's conclusion onto the code. Confidence: 0.7
- GitHub-remote hard-replacement missions (Owner declares the remote a stale backup to be overwritten with the current factual worktree — REPLACE FORWARD, never merge/reconcile and never GITHUB → filesystem) run a fixed protocol: PHASE 1 factual inventory of the worktree only (branch/remote read as metadata, git history never consulted as design authority, absence on disk is a fact and deleted files are never restored to satisfy the remote); PHASE 2 remote identification limited to proving the exact target repo+branch (`git remote -v`, `git ls-remote`) — remote content/history is never read to decide design; PHASE 3 pre-replace safety proof including a staged-content secret audit (`git diff --cached --name-only` filtered for .env/credential/key/service-account patterns — sensitive files must be proven absent from the staged set via the CURRENT factual .gitignore, never the old remote's; source + example env files only) and an explicit no-backward-import statement; PHASE 4 hard replace via one snapshot commit of the entire worktree (`git add -A`) + force push to the verified branch ONLY because the Owner explicitly commanded REPLACE and only after the target is verified — never force-push to an unverified repo/branch and never pull/fetch/checkout/merge remote state before pushing (uncommitted/dirty worktree is the factual baseline being snapshotted, not something to reset or clean to please the remote); PHASE 5 post-replace proof by ref equality (`git ls-remote origin <branch>` == `git rev-parse HEAD`). STOP-and-report to the Owner (never merge/restore to resolve) on: unprovable remote identity, secret ambiguity, filesystem ambiguity, push failure, or a non-fast-forward conflict that would require design recovery. Confidence: 0.7
- Forbids git rollback/restore commands (checkout, restore, reset, clean, stash, cherry-pick, revert); repairs must be written forward on the current filesystem, and reversing one's own mistakes should use the edit/session history of the exact hunks introduced — not git. Confidence: 0.9
- Demands narrow, bounded work slices with explicit protected/out-of-scope lists, forbidden actions, and stop conditions; strongly rejects cross-domain scope creep (e.g., finance/payment/coins/refund code must not be touched during content/share work). Confidence: 0.9
- Never skips, trims, or "neutralizes" tests to make a package compile; newly skipped safety tests are unacceptable — fix root causes or report the blocker. Confidence: 0.8
- Tests that pin a canonical contract are treated as evidence of intended design even when they fail to compile against the current tree; when production lacks the fields/methods the canonical design requires, repair production AND the test contract in a bounded way — never delete a test merely because it currently fails. Confidence: 0.85
- Tests that describe a design the owner explicitly rejected (e.g., a delete-media endpoint) are replaced with a decision-lock test asserting the rejected artifact is ABSENT (route/logic not registered), preserving a documented decision trace — never silently deleted and never left as a t.Skip (skip does not fix compilation of the test body). Confidence: 0.7
- When a contract test pins both in-scope and out-of-scope (protected-domain, e.g., Commerce) features, the out-of-scope assertions are removed and only in-scope assertions retained — the protected-domain feature is never implemented merely to satisfy the test. Confidence: 0.7
- When a failing test encodes the locked canonical contract and the production code retains the rejected residue (e.g., a local reserved-name list contradicting the backend authority), the test is evidence against the residue: fix the production code to satisfy the contract and keep the test intact — never "fix" the test or classify it as stale. Confidence: 0.7
- When a focused task is blocked by unrelated package-wide compile/test debt, prefers isolated explicit-file test invocations and does not treat unrelated package-wide debt as an acceptance gate. Confidence: 0.7
- Prefers forward-only, surgical fixes; when reversing accidental changes, do not "modernize" or independently repair unrelated stale APIs. Confidence: 0.7
- Prefers documentation to be authoritative: docs extracted from the codebase are revised until final, and afterwards the codebase must follow the docs. Confidence: 0.7
- Wants full-suite verification run in a clean window (no other processes mutating the shared test database) with the complete package — no selective test filtering. Confidence: 0.6
- Cleanup doctrine for rejected implementations: anything proven to represent a rejected model must be deleted, not deprecated and never kept "for compatibility" — no dead functions, comments, fixtures, tests, aliases, or documentation left behind that could resurrect it (enabled by zero-production-data / no-backward-compatibility policy); residue must be proven clean by semantic search, not assumed. Confidence: 0.95
- Before modifying code that depends on a data field, trace the exact data path and verify the canonical field is genuinely available; if unavailable, STOP and report PROOF_INCOMPLETE rather than inventing a substitute denominator/value. Confidence: 0.85
- Stop-and-escalate rule: if implementation reveals a new contradiction in business/accounting authority outside the authorized scope, STOP and report it as a blocker for owner/architecture decision — never solve the newly-discovered contradiction opportunistically. Explicit stop conditions include two genuinely incompatible business interpretations, a missing owner decision, a ledger movement with undefined funding source, a canonical formula contradicting an actual ledger invariant, uncertainty whether an artifact is stale or intended, and a test whose expectation contradicts the locked canonical contract — do not guess; STOP if the existing code does not establish the funding contract. Confidence: 0.95
- Treats the mere existence of an artifact (untracked test, migration, cmd tool) as NO evidence of intent: stale residue is not implemented merely because it exists, APIs are never resurrected just to make stale tests compile, and canonical production code is never adapted to satisfy tests that encode a rejected contract — stale-layer status must be proven by a separate audit establishing an independent canonical requirement. Confidence: 0.8
- Validation ordering for implementation changes: run the focused package tests first, then directly affected package tests, then broader related packages, then go vet for the affected packages. Confidence: 0.8
- Frames implementation tasks as "executor, not architect": implement exactly the locked spec/scope, do not redesign, invent new formulas, or add new authorities during execution — architectural decisions belong to the audit/owner, not the implementation pass. Confidence: 0.7
- Auth login-completion implementation tasks run on a forbidden-design contract that is enforced during the fix (not just recommended): never manually navigate/push/go to `/home` after a Firebase success (would hide backend/auth failure and create a second navigation authority), never split email vs Google backend-sync paths, never create a duplicate `_syncWithBackend`, never add a fallback `catch (_) { state = authenticated }` that treats Firebase success as backend-authenticated without backend proof, never hide a backend failure as empty/idle/unauthenticated with no user-visible explanation, never keep listener-only completion as the sole way explicit login reaches authenticated, and never add a compatibility wrapper to keep a legacy service alive. Confidence: 0.7
- Auth login-completion listener race is closed with a listener-deferral guard, not only the sync mutex: during an explicit login (`_isExplicitLoginInProgress` / `_isInitiatingEmailSignup`), the Firebase `authStateChanges` listener updates the intermediate firebase-authenticated state but then returns early WITHOUT invoking `_syncWithBackend`, while the initiator (`signInWithEmail`/`signInWithGoogle`) awaits `_syncWithBackend` directly as the deterministic completion authority — because the in-progress `_syncedUserId` mutex alone cannot dedupe the listener's second exchange on the FAILURE path (`_syncedUserId` is set only on success, so on a first-attempt failure a loser would re-run a duplicate exchange). Confidence: 0.65
- Auth login-completion implementation requires explicit-login completion to NOT depend solely on the Firebase `authStateChanges` listener: the explicit `signInWithEmail`/`signInWithGoogle` success path must await the canonical backend sync directly (with listener events de-duped against the same sync guards, so explicit-plus-listener yields ONE exchange, no double credential write, no stale overwrite, no double authenticated publish) — listener-timing/ordering/guard/duplicate/initial-event failure must never strand a successful login. Confidence: 0.75
- Auth login-completion implementation requires behavioral test proofs that go through the REAL flow, never by forcing state directly to authenticated: explicit email login (login action → Firebase success → canonical backend sync → AuthStateAuthenticated → router /home) and explicit Google login via the same architecture seam; listener-ordering protection (explicit completes then listener is delayed, and listener event arrives while explicit sync active — proving one sync authority, no stranded login, no duplicate exchange, correct terminal state); backend-failure and backend-unavailable screen proofs (Firebase success → exchange failure → visible error on SignInScreen, no redirect /home, retry available, no silent stuck); credential-authority proof (login + profile-completion + refresh rotation + logout clear all through the same canonical persistence boundary); and a legacy negative contract that fails if listener-only explicit completion, the legacy Firebase service authority, legacy token methods, or dual independent credential persistence ownership is reintroduced. Confidence: 0.7
- Implementation-executor turns for this domain may run continuously until clean ("KERJAKAN IMPLEMENTASI SAMPAI CLEAN") — the report is written AFTER the changes are complete rather than a long pre-change report — while still keeping the audit-vs-implementation separation: a bounded implementation session proceeds through its fixed phase order (baseline → canonical fix → failure visibility → credential convergence → field purge) and only the final required report is produced at the end. Confidence: 0.6
